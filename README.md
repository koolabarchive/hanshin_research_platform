# 한신 리서치풀

한신대학교 일반대학원 연구자를 위한 연구참여자 모집 플랫폼입니다.

참여자는 대기풀에 조건을 한 번 등록해 두면 맞는 연구가 열릴 때 안내를 받고, 연구자는 참여자의 이름과 연락처를 모른 채 가명 ID로만 모집·안내·보상을 처리합니다. 모든 연구는 연구윤리지원팀이 IRB 승인을 확인한 뒤 공개됩니다.

화면과 흐름은 시연용 프로토타입(단일 HTML)을 그대로 따르되, 브라우저 저장소 대신 실제 서버(로그인, 권한 검사, 암호화)가 처리하고 데이터는 모두 **Cloud Firestore**에 저장합니다.

## 구조

```
브라우저 (public/)  ──/api──▶  서버 (src/, Express)  ──Admin SDK──▶  Cloud Firestore
```

- 브라우저는 Firestore에 직접 접근하지 않습니다. `firestore.rules`가 모든 직접 읽기·쓰기를 막고, 서버만 Admin SDK로 접근합니다.
- 이렇게 한 이유: 연구자에게 참여자 정보를 가리는 일, 대기풀에서 조건에 맞는 사람을 골라 초대하는 일, 예약 정원 관리, 메일·문자 발송은 브라우저 코드와 보안 규칙만으로는 안전하게 할 수 없습니다.
- 서버는 두 가지 방식으로 돌릴 수 있습니다: Firebase Hosting + Functions(`index.js`), 또는 서비스 계정 키를 가진 일반 서버(`npm start`).

## 실행 (로컬, Firestore 에뮬레이터)

Node.js 22 이상과 Java(에뮬레이터용)가 필요합니다. 터미널 두 개를 씁니다.

```bash
npm install
npm run emulator
```

```bash
npm run seed
npm run dev
```

http://localhost:3000 을 열고 `로그인`을 누르면 시연 계정(참여자·연구자·관리자) 버튼이 보입니다. 시연 데이터는 모두 가상이며 메일·문자가 실제로 나가지 않습니다. 에뮬레이터의 데이터는 끄면 사라집니다(`npm run seed -- --reset`으로 다시 넣을 수 있습니다).

테스트: `npm test` (에뮬레이터를 따로 띄우지 않은 상태에서 실행합니다. 직접 띄웠다가 내려 줍니다.)

## 역할별 흐름

| 역할 | 할 수 있는 일 |
| --- | --- |
| 참여자 | 가입(이메일 인증번호) → 대기풀 등록·일시정지 → 맞는 연구 확인 → 설명문 확인 → 전자동의(성명 서명) → 일정 예약·설문 → 보상. 알림함, 연구자에게 문의, 참여 철회(응답 폐기 선택), 탈퇴 |
| 연구자 | 학교 메일 가입 + 윤리교육 이수증 → 7단계 연구 등록(설명문·동의서·설문지·조건·안내 문구·보상) → 심사 제출 → 대기풀 초대, 단계별 안내 발송, 공지, 문의 답변, 참여 완료 처리, 보상 지급 처리, 응답 데이터·지급 대장 복사 |
| 관리자(연구윤리지원팀) | 연구자 재학·이수 확인, 연구 심사(승인·보완 요청), 모바일 상품권 발송, 처리 기록 열람 |

### 참여자 범위: 교내 구성원과 학외 일반인

- 학부생·대학원생·교직원은 학교 메일(@hs.ac.kr)로만 가입합니다. 학교 메일이 곧 소속 확인입니다.
- 학외 일반인은 개인 메일로 가입하며, 연구자에게 `학외 일반인`으로 구분되어 보입니다.
- 연구마다 참여 조건의 `신분`에서 대상 범위를 정합니다. `학외 일반인`을 넣지 않은 연구는 학외 참여자에게 안내가 가지 않고 신청도 받지 않습니다.

## 누가 무엇을 볼 수 있나

화면에 필요한 데이터는 서버가 로그인한 사람의 역할에 맞춰 걸러서 내려 줍니다(`src/state.js`). 화면 코드에서 숨기는 것이 아니라, 애초에 보내지 않습니다.

| 정보 | 참여자 본인 | 연구자 | 연구윤리지원팀 |
| --- | --- | --- | --- |
| 이름, 이메일 | O | X | X |
| 휴대전화 | O | 끝 4자리 | 상품권 발송 대기 건만 전체, 발송 후 끝 4자리 |
| 매칭 정보(출생연도·성별·학과 등) | O | 신분·연령대만 | X |
| 대기풀 | - | 조건별 인원수, 20명 이상일 때 분포 | - |
| 설문 응답 | O | 자기 연구의 가명 응답 | X |
| 전자서명·동의서 사본 | O | 동의 일시만 | X |
| 이수증·IRB 승인 통지서 | - | 본인이 올린 것 | O (열람 기록 남음) |

그 밖의 보호 장치:

- 이름·연락처, 매칭 정보, 설문 응답, 서명은 서버가 암호화(AES-256-GCM)한 뒤 Firestore에 저장합니다. Firestore 콘솔에서 문서를 열어도 내용이 보이지 않고, 키(`DATA_KEY`)는 Firestore가 아닌 곳에 둡니다.
- 한 사람에게 가는 모집 안내는 일주일에 3번까지입니다. 연구자가 직접 쓰는 안내는 연구당 하루 3번까지입니다.
- 연구 등록 화면의 "조건에 맞는 인원"은 5명 미만이면 정확한 수를 알려 주지 않습니다(조건을 좁혀 개인을 짚어내는 것 방지).
- 문의는 가명 ID로 전달되고 답변도 플랫폼이 전달합니다. 연구자는 부적절한 문의를 신고해 가릴 수 있습니다.
- 동의·예약·완료·지급·승인처럼 상태가 바뀌는 지점은 Firestore 트랜잭션으로 처리합니다. 동시에 신청해도 예약이 정원을 넘지 않고, 같은 건이 두 번 지급되지 않습니다.
- 비밀번호는 scrypt 해시(로그인은 Firebase Auth가 아니라 이 서버가 처리), 세션 쿠키는 HttpOnly·SameSite, 상태를 바꾸는 요청은 CSRF 토큰 필요, 로그인·가입·인증번호 요청은 횟수 제한, 인라인 스크립트를 막는 CSP.

## 프로토타입과 달라진 점

- **학외 일반인** 신분과 **상담·프로그램** 연구 유형을 추가했습니다.
- **연구자에게 문의하기**를 만들었습니다(프로토타입 문구에는 있었지만 기능이 없었음).
- **모바일 상품권 발송**: 연구자는 번호를 모르므로, 연구자가 지급 처리하면 연구윤리지원팀의 `보상 발송` 목록에 올라가고, 실제로 보낸 뒤 `발송 완료`를 누르면 참여자에게 발송 문자가 나갑니다. 현금은 연구자의 지급 처리로 끝납니다.
- 비밀번호 재설정, 이수증·IRB 통지서 실제 업로드(PDF/JPG/PNG, 5MB)와 연구지원팀 내려받기를 추가했습니다.
- 시연 계정 버튼과 시연 안내 띠는 `DEMO_MODE=1`일 때만 보입니다. 데이터 초기화 버튼은 없앴습니다.
- 가명 ID는 가입 순서가 드러나지 않도록 무작위 번호입니다.

## 폴더 구조

```
public/
  index.html, app.css   화면 틀과 스타일(프로토타입 그대로)
  app.js                화면 코드: 서버가 준 데이터를 그리고 동작을 서버에 전달
src/
  server.js             HTTP 서버, 보안 헤더, API 경로
  state.js              역할별로 내려 줄 데이터 구성 ← 노출 범위는 여기서 결정
  actions.js            모든 동작(가입·등록·초대·동의·지급·심사 등)과 권한 확인
  domain.js             매칭, 초안 검증, 제출 조건 등 규칙
  db.js, store.js       Firestore 연결, 조회·발송·처리 기록 (컬렉션 설명은 db.js)
  jobs.js               자동 리마인더, 방문 하루 전 안내, 모집 기간 종료 마감
  auth.js, security.js  세션·CSRF·횟수 제한, 비밀번호 해시·암호화
  mailer.js             이메일(SMTP)·문자 발송
index.js                Firebase Functions 진입점(HTTP 함수 app, 예약 함수 jobs)
firebase.json           Hosting·Functions·에뮬레이터 설정
firestore.rules         브라우저의 직접 접근 전면 차단
firestore.indexes.json  복합 색인
scripts/                시연 데이터, 관리자 계정 생성
test/                   규칙 테스트, 가입부터 보상까지의 API 테스트
```

학과 목록, 관심 분야, 연구 유형 같은 선택지는 `src/domain.js`와 `public/app.js` 맨 위의 상수를 함께 고칩니다.

## Firebase에 올리기

아래 절차와 `index.js`·`firebase.json`의 Hosting·Functions 설정은 **실제 Firebase 프로젝트에 배포해 확인하지 못했습니다**(이 저장소의 검증은 모두 에뮬레이터에서 했습니다). 처음 배포할 때 단계마다 확인이 필요합니다.

1. Firebase 프로젝트를 만들고 Firestore 데이터베이스를 **서울(asia-northeast3)** 리전, 운영 모드로 만듭니다. 리전은 나중에 바꿀 수 없습니다.
2. Functions를 쓰려면 Blaze(종량제) 요금제가 필요합니다. 무료(Spark) 요금제로는 서버 코드를 Firebase에 올릴 수 없고, 이 경우 서버를 학교 서버 등 다른 곳에서 돌려야 합니다(아래 "일반 서버에서 돌리기").
3. 프로젝트 연결, 암호화 키 등록, 배포:

   ```bash
   npx firebase login
   npx firebase use --add
   node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
   npx firebase functions:secrets:set DATA_KEY
   npx firebase deploy
   ```

4. 첫 관리자 계정은 서비스 계정 키가 있는 컴퓨터에서 만듭니다.

   ```bash
   GOOGLE_APPLICATION_CREDENTIALS=./serviceAccount.json DATA_KEY=... ADMIN_EMAIL=... ADMIN_PASSWORD=... npm run create-admin
   ```

5. 메일·문자 발송 설정(`SMTP_*`, `SMS_*`)도 `DATA_KEY`처럼 secret으로 등록하고 `index.js`의 `secrets` 목록에 추가해야 함수에서 읽을 수 있습니다.

알아 둘 점:

- **색인**: 에뮬레이터는 복합 색인이 없어도 쿼리가 돌기 때문에 `firestore.indexes.json`이 충분한지는 실제 프로젝트에서만 확인됩니다. 색인이 부족하면 해당 화면에서 오류가 나고, Functions 로그에 색인을 만드는 링크가 찍힙니다.
- **쿠키**: Firebase Hosting은 서버로 `__session` 쿠키만 넘겨주므로 세션과 CSRF 토큰을 이 쿠키 하나에 담았습니다.
- **비용**: Firestore는 읽은 문서 수만큼 과금됩니다. 연구자 화면은 자기 연구의 참여 기록을 통째로 읽으므로(연구당 수백 건), 대기풀 목록(60초)과 연구별 참여 기록(15초)을 서버 메모리에 잠깐 기억해 읽기를 줄였습니다. 인스턴스가 여러 개 뜨면 화면 숫자가 그 시간만큼 늦게 맞을 수 있습니다. 사용량이 늘면 화면별로 필요한 것만 읽도록 API를 나누는 것이 다음 단계입니다.
- **횟수 제한**(로그인·가입·인증번호)은 인스턴스 메모리에서 셉니다. `index.js`에서 `maxInstances`를 낮게 잡아 두었지만, 엄격한 제한이 필요하면 Firestore나 App Check로 옮겨야 합니다.
- **첨부 파일**(이수증·IRB 통지서)은 Firestore 문서에 나눠 저장합니다(파일당 최대 5MB). 양이 많아지면 Cloud Storage로 옮기는 편이 낫습니다.
- `firebase` 패키지(브라우저용 SDK)는 설치되어 있지만 쓰지 않습니다. 서버는 `firebase-admin`을 씁니다.

### 일반 서버에서 돌리기

Functions 없이 Firestore만 쓰는 방법입니다. 서비스 계정 키를 내려받아 서버에 두고 실행합니다.

```bash
GOOGLE_APPLICATION_CREDENTIALS=/path/serviceAccount.json NODE_ENV=production npm start
```

나머지 설정은 `.env.example`을 참고합니다. 이 경우 주기 작업은 서버가 30분마다 직접 돌립니다.

## 운영 전에 해야 할 일

1. **IRB·개인정보 보호책임자 검토.** 대기풀 운영 방식, 가입 화면의 수집·이용 동의 문구, 전자동의 방식(성명 입력 서명)이 학교 기준에 맞는지 확인받아야 합니다. 동의서 원본을 연구자가 아니라 플랫폼이 보관하는 방식도 IRB와 합의가 필요합니다.
2. **외부 클라우드 보관에 대한 검토.** 참여자 정보가 학교 서버가 아니라 Google Cloud(Firestore)에 저장됩니다. 서울 리전을 쓰고 민감한 항목은 암호화해 두었지만, 개인정보 처리 위탁에 해당하므로 처리방침 기재와 학교의 승인이 필요합니다.
3. **학교 로고 사용 승인.** 화면에 한신대학교 엠블럼과 로고가 들어 있습니다.
4. **보상 발송 주체 결정.** 지금은 연구윤리지원팀이 상품권을 직접 보내는 구조입니다. 연구비 집행 절차와 맞는지 확인하고, 필요하면 상품권 발송 업체 API 연동으로 바꿉니다.
5. **암호화 키(`DATA_KEY`) 보관.** 잃어버리면 저장된 정보를 복구할 수 없습니다. Secret Manager 외에 별도 사본을 안전한 곳에 둡니다.
6. **이메일(SMTP)과 문자 발송 계정 연결.** 연결 전에는 메일·문자가 실제로 나가지 않고 `outbox` 컬렉션에만 쌓입니다. 문자 업체의 요청 형식에 맞게 `src/mailer.js`의 `sendSms`를 고쳐야 합니다.
7. **백업과 폐기.** Firestore 예약 백업을 켜고, 법정 보관 기간이 지난 동의서·응답의 폐기 절차를 정해야 합니다(자동 폐기는 아직 없습니다).

## 아직 없는 것

- 본인 확인은 이메일 인증뿐입니다. 학외 참여자는 한 사람이 여러 계정을 만들 수 있습니다.
- 가입 후 이름·휴대전화·출생연도·신분을 직접 고치는 화면이 없습니다(관심 분야·시간·수신 설정만 수정 가능).
- 종단 연구의 회차별 일정·리마인더, 상담 프로그램의 회기별 출석 관리는 없습니다. 한 번의 예약과 한 번의 설문만 다룹니다.
